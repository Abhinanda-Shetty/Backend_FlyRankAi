# Task Management CRUD API

A simple, lightweight RESTful API built with Node.js, Express, and SQLite using `better-sqlite3` to manage tasks. Tasks are persistently stored in a local SQLite database, and the API provides interactive documentation through Swagger UI.

This project has been extended with **Supabase Auth** — the API now supports sign up, log in, and log out, and specific routes are protected behind JWT verification. See the [Authentication](#authentication) section below for full details.

---

## Features

* **Full CRUD operations**: Create, Read, Update, and Delete tasks.
* **SQLite Persistence**: Tasks are stored persistently in a local SQLite database instead of an in-memory array.
* **Payload Validation**: Validates required fields when creating or updating tasks.
* **Automatic ID Generation**: Task IDs are generated by SQLite.
* **Interactive Documentation**: Built-in Swagger UI generated from an `openapi.json` schema.
* **Health Check**: Provides an endpoint to verify that the server is running.
* **Authentication (new)**: Sign up, log in, and log out via Supabase Auth.
* **Protected Routes (new)**: JWT-verified, reusable auth middleware guards specific endpoints.

## Getting Started

### 1. Prerequisites

Ensure you have **Node.js** installed on your local machine.

SQLite does not require a separate database server. The application uses `better-sqlite3` to create and interact with the local SQLite database file.

You will also need a free **Supabase** project ([supabase.com](https://supabase.com)) — no credit card required — for authentication.

### 2. Environment Variables

Create a `.env` file in the project root (this file is git-ignored and never committed):

```
SUPABASE_URL=your_project_url
SUPABASE_KEY=your_anon_key
PORT=3000
```

Get `SUPABASE_URL` and `SUPABASE_KEY` (the **anon** key — never the `service_role` key) from your Supabase Dashboard under **Project Settings → API**.

> **Supabase setting:** under **Authentication → Sign In / Providers → Email**, turn **"Confirm email" off** so a freshly signed-up user can log in immediately without checking an inbox.

A `.env.example` is committed with the key names and placeholder values — copy it to `.env` and fill in your own values.

### 3. Installation

Navigate to the root of the project directory and install all required dependencies from `package.json`:

```bash
npm install
```

### 4. Run the Server

Launch the application using:

```bash
npm run dev
```

The terminal should display a message similar to:

```text
Server is running on port 3000
```

The SQLite database will be created/used locally by the application, and the server connects to Supabase using your `.env` values.


## Sample Request Payloads

### Create Task (`POST /tasks`)

**Body:**

```json
{
  "title": "Finish code assessment"
}
```

### Update Task (`PUT /tasks/1`)

**Body:** You can provide either or both fields.

```json
{
  "title": "Review final submission",
  "done": true
}
```

### Sign Up (`POST /auth/signup`)

```bash
curl -i -X POST http://localhost:3000/auth/signup \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"password123"}'
```

### Log In (`POST /auth/login`)

```bash
curl -i -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"password123"}'
```

Response includes an `access_token` — copy this for the requests below.

### Access a Protected Route (`GET /protected/profile`)

```bash
curl -i http://localhost:3000/protected/profile \
  -H "Authorization: Bearer <PASTE_ACCESS_TOKEN>"
```

### Log Out (`POST /auth/logout`)

```bash
curl -i -X POST http://localhost:3000/auth/logout \
  -H "Authorization: Bearer <PASTE_ACCESS_TOKEN>"
```

## Authentication

This API never hashes passwords or signs tokens itself — that responsibility belongs entirely to **Supabase**, the Identity Provider:

1. **Sign up / Log in** — the client sends credentials to this server, which forwards them to Supabase.
2. **The token** — Supabase verifies the credentials and returns a signed JWT (`access_token`).
3. **The request** — the client attaches that JWT to future requests via `Authorization: Bearer <token>`.
4. **Verification** — a reusable middleware function asks Supabase, on every protected request, "is this token real?" (`supabase.auth.getUser(token)`). Only a valid, unexpired, unmodified token is allowed through.

All protected routes (`/protected/profile`, `/protected/dashboard`, `/auth/logout`) share this one middleware — the verification logic exists in exactly one place, so any change to how tokens are checked only has to happen once.

## Data Persistence

Previously, tasks were stored in an in-memory array. This meant that all tasks were lost whenever the server restarted.

The application now uses **SQLite with `better-sqlite3`** for persistent storage. Tasks are saved in a local database file and remain available after restarting the server.

```text
   │
   ▼

   │
   ▼

   │
```

Swagger UI provides an interactive interface for testing all available endpoints, including authorized calls to protected routes.

## Notes

* The SQLite database is stored locally as a database file used by the application.
* No separate database server is required for tasks.
* Make sure the application has permission to create and write to the database file.
* The database file should generally be excluded from version control if you do not want to commit local application data.
* `.env` is git-ignored and never committed — only `.env.example` (with placeholder values) is tracked.
* No Supabase keys appear anywhere in this repo's git history.
* This server uses the Supabase **anon** key, which is safe to expose client-side; the `service_role` key is never used here.
* Access tokens are short-lived JWTs (Supabase default: 1 hour) and, being stateless, remain valid until they expire — logging out ends the Supabase session but does not retroactively invalidate an already-issued token still within its expiry window.
